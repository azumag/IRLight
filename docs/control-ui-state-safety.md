# Control UI state freshness and fail-closed behavior

The Phase 0 Control UI polls `/api/status` once per second and treats the response as an observation, not as durable UI truth. The runtime timestamp is accepted only while it is within the existing three-second freshness window. The browser also ages the last successful snapshot using both the status request duration and time elapsed since receipt, so a slow or hanging request, a suspended tab that resumes, or a temporarily stalled polling loop cannot leave or restore an old LIVE state as current. A backwards client clock jump beyond the small tolerance is treated as untrusted rather than extending freshness. When the effective runtime age is stale, runtime-derived session/video/input/actual/version fields are replaced with `状態確認不能`, while the freshly read desired control state may still be shown. Audio actions remain disabled while the runtime is stale, the actual audio mode is unknown, or the latest control command has not been acknowledged.

If a status poll fails, the UI must not continue presenting values from the last successful response as though they were current. Session, video source, input presence, desired/actual audio state, control/runtime version, and last-update fields are replaced with `状態確認不能`; the audio action is disabled and shown with the neutral unavailable style. A later successful poll repopulates the fields from the newly fetched snapshot.

Screen-reader announcements are intentionally separated from the one-second polling grid. The grid itself is not a live region because its timestamp and other fields change frequently and would otherwise create continuous announcement noise. A dedicated visually-hidden polite/atomic status region announces only semantic session/audio state changes and de-duplicates identical summaries. Repeated identical polling failures likewise do not rewrite the existing alert text, while a genuinely new error still uses the existing `role="alert"` path. Polling failures and audio-control feedback are tracked separately: a successful background status poll clears only the polling error, so a control conflict or unknown command outcome is not erased by the next one-second refresh. Action feedback is cleared deliberately when the user starts a new audio action. The status grid, audio-control card, and Phase 0 safety notice are exposed as explicitly named regions via visually-hidden headings and `aria-labelledby`, so landmark/heading navigation gives each area a stable purpose without adding visual chrome. The primary audio action also has an explicit `:focus-visible` ring, with a forced-colors override, so keyboard focus remains visually identifiable without changing pointer-focus behavior. The button is exposed as an ARIA toggle only while the runtime snapshot is fresh, the actual mode is known, and the latest command identity/version has been acknowledged. In that trusted state, `aria-pressed` reflects the user-requested mute mode (`MUTED`), rather than incidental silence such as `SILENT_FALLBACK`; when the state is stale, unknown, or unacknowledged the attribute is removed instead of asserting a false on/off state. The accessible toggle name is kept stable as `配信音声をミュート` even though the visible next-action text changes, so the meaning of `aria-pressed` does not invert with the label. The explanatory mute/continuity text is associated with the button through `aria-describedby`. A separate polite/atomic action live region announces when a mute or unmute command is being sent, while `aria-busy=true` is present only during that in-flight request. The transient announcement is cleared when the request finishes so a later retry of the same requested mode can be announced again. This keeps action progress separate from the de-duplicated polling-state live region and from `role="alert"` error feedback.

The status grid is also constrained for narrow mobile viewports. Value cells and badge text are allowed to shrink and wrap instead of forcing horizontal overflow, and viewports at 24rem or narrower use two explicitly shrinkable grid columns. This keeps label/value pairs side by side for quick scanning without allowing long status text to push the control surface wider than the device. A compact visual Session/audio summary stays at the safe-area-aware top edge with `position: sticky`, so the two highest-priority states remain visible while the detailed status grid scrolls out of view. The sticky summary is `aria-hidden` because it duplicates the canonical named status region and semantic live announcement; assistive technology should receive the state once rather than traversing a second visual copy. The one-second periodic poll is skipped while the document is hidden, reducing unnecessary mobile data and battery use without treating the cached snapshot as current. When a suspended/backgrounded tab becomes visible again, the UI immediately re-renders the cached snapshot through the same freshness checks and starts a status refresh instead of waiting for the next one-second timer tick. A BFCache restore uses the same path. The existing single-flight guard prevents the wake-up refresh from creating overlapping `/api/status` requests. Status and audio-control HTTP requests are also bounded to five seconds with `AbortController`. The status deadline remains armed through JSON body consumption, so a server that sends headers and then stalls the body cannot wedge the single-flight slot. Audio control only consumes the response status before reconciling through `/api/status`, so its timed scope covers the entire response data the UI trusts. A stalled request therefore cannot leave the single-flight slot or action-busy state wedged indefinitely. Runtime values still fail closed at the stricter three-second freshness boundary while a slow status request is in flight.

A failed or timed-out `PUT /api/audio` is also treated as an unknown outcome. The UI closes actions first, re-reads `/api/status`, and only re-enables control after a fresh authoritative snapshot satisfies the same freshness and command-acknowledgement checks. It does not retry the toggle with a new idempotency key.

This remains a Phase 0 local-only surface. It does not replace the Session-authenticated control API or change the deployment/security boundary described in `AGENTS.md`.

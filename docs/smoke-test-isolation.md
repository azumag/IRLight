# Smoke test isolation

IRLight smoke tests that create Docker Compose resources must not borrow or tear down a developer or operator Compose project.

## Required contract

For destructive/disposable smoke environments:

- generate a Compose project name for each test process and pass it explicitly with `docker compose -p`;
- do not inherit `COMPOSE_PROJECT_NAME` as the identity of the disposable test environment;
- never run a pre-test `down`, `rm`, volume removal, or prune operation against an implicitly resolved project;
- cleanup only the project generated by that test run;
- keep cookies, temporary credentials, generated certificates, and diagnostic logs under a per-run private temporary directory with a restrictive umask;
- when generated secrets or certificates are written during setup, arm a temp-directory-only `EXIT` guard immediately after `mktemp -d`, before the first secret/material write; replace that guard with the normal full cleanup trap only after the Compose-aware cleanup path is safe to call;
- if a fixed host port is already occupied, fail the smoke rather than stopping the existing service that owns the port.

The early temp guard must only remove that run's private temporary directory. It must not inspect logs, invoke Docker/Compose, or mutate project resources that may not have been initialized yet. The later full cleanup remains responsible for diagnostics and teardown once the disposable project lifecycle has been established.

The disposable project may remove its own volumes during cleanup. This permission does not extend to any pre-existing project or resource.

## Bounded probe output

Readiness and diagnostic probes running under `set -o pipefail` must not use an early-exiting consumer such as `grep -q` directly on a producer whose exit status matters. A successful match can close the pipe before the producer finishes, causing SIGPIPE and turning a successful observation into a false negative.

For bounded command output, capture the producer's complete output into a run-local private temporary file first, require the producer itself to succeed, and only then inspect the saved output. `scripts/smoke-rtmps-ingest-recovery-core.sh` follows this contract for the four-second `openssl s_client` RTMPS-listener probe. This keeps the existing per-attempt and overall readiness deadlines while separating command failure from a missing certificate marker.

## Secret-bearing diagnostics

A smoke test that deliberately injects a generated credential or stream key must assume that a regression can place that value in status output or service logs. Failure diagnostics therefore must not print raw producer output directly to CI stderr.

Capture diagnostic output inside the run-local private temporary directory, redact every generated secret before emitting it, and withhold the output entirely if redaction fails. Secret-absence assertions must also separate log-read failure from a genuine no-match result; a failed log read is not evidence that the secret was absent. In particular, do not use `docker compose logs | grep -q <secret>` under `set -o pipefail`, because a successful match can terminate `grep` early and turn the upstream SIGPIPE into a false-negative leak check. Generated secrets should also stay out of helper process command lines: persist them in a run-local `0600` file and pass only that file path to redactors/assertion helpers so process listings and runner diagnostics cannot expose the secret value.

`scripts/smoke-egress-stop-terminal.sh`, `scripts/smoke-egress-publish-conflict.sh`, and `scripts/smoke-ingest-auth-cache.sh` follow this fail-closed diagnostic boundary. The publish-conflict smoke persists its generated stream key in a private redaction-value file before constructing the disposable target config and URL, then unsets both the key and its secret-derived path. Status JSON is validated from stdin, while the holder/publish-conflict proof reconstructs the expected target path inside a helper from the private secret file; neither the raw status payload nor the generated key/path is passed in helper argv. The stop-terminal smoke accumulates both its initial destination key and the later unsafe-destination test key in one private redaction-value file, unsets each shell value after constructing its disposable URL, and feeds status JSON to validators over stdin so neither generated secret nor potentially secret-bearing status payloads enter helper argv. The auth-cache smoke keeps its generated ingest username/secret in a private redaction-value file instead of putting those values on the redactor process command line, and withholds service diagnostics if credential issuance completed before the redaction value was safely persisted. `scripts/smoke-egress-reconnect.sh` likewise writes its generated stream key to a private file, unsets the shell value after constructing the disposable target URL, and lets redaction, leak checks, and target-path assertions read only that file path rather than receiving the secret in helper argv. `scripts/smoke-egress-dns-tls.sh` applies the same helper-argv boundary to its generated TLS stream key and additionally parses potentially secret-bearing status JSON from stdin rather than placing the payload on a helper command line. `scripts/smoke-egress-secret-delivery.sh` uses the stricter quarantine variant because it simultaneously handles login/session material, a bootstrap token, a plaintext Destination stream key, and the resolved credentialed URL: raw service logs are never replayed to CI on failure, and secret-bearing API assertions use fixed messages rather than embedding response payloads. `scripts/smoke-ingest-disconnect-recovery.sh` uses the same strict quarantine approach because the publisher URL contains an issued ingest username/secret: service and publisher logs stay in the private run directory, and Session/event/Node timeout paths emit only fixed diagnostic context. `scripts/smoke-hold-timeout-cleanup.sh` handles login cookie/CSRF material before exercising the reaper, so its failure cleanup does not replay raw `control-ui` service logs; it retains only the existing non-auth Session/provider state evidence needed to diagnose HOLD_TIMEOUT cleanup. The public `scripts/smoke-continuity-restart.sh` entrypoint uses the strongest public-wrapper boundary for restart reconciliation: the credential-bearing implementation lives in `scripts/smoke-continuity-restart-core.sh`, all core stdout/stderr including raw Continuity/MediaMTX logs and `/api/status` timeout payloads stays in a run-local private wrapper log, and CI receives only fixed allowlisted success/failure messages. The continuity-restart core must not be invoked directly by CI. The public `scripts/smoke-short-media-stall.sh` entrypoint now applies the strongest quarantine boundary: the credential-bearing implementation lives in `scripts/smoke-short-media-stall-core.sh`, all core stdout/stderr including build logs, continuity state, service logs, publisher output, and raw timeout/assertion payloads is captured in a private wrapper log, and CI receives only fixed allowlisted success/failure messages. The public `scripts/smoke-rtmp-netem-blackhole.sh` entrypoint applies the same strongest quarantine boundary: the credential-bearing behavior remains in `scripts/smoke-rtmp-netem-blackhole-core.sh`, all publisher/service/state/Session/event/Node diagnostics stay inside a run-local private wrapper log, and CI receives only fixed allowlisted success/failure messages. ## Parallel execution

A unique Compose project name prevents project/volume/name collisions, but it does not by itself make tests with fixed published host ports parallel-safe. Tests that expose fixed ports must either allocate test-specific ports or fail cleanly on collision without changing unrelated containers.

## CI runtime proof

`scripts/ci-smoke-compose-isolation-runtime.sh` wraps the central `smoke-compose.sh` scenario inside the shared Docker CI suite. It turns the isolation contract into an actual Docker runtime regression rather than relying only on source inspection:

1. Start an unrelated, uniquely named sentinel Compose project with its own named volume and marker data.
2. Start the real central smoke while the sentinel remains running.
3. After the first smoke exposes `/healthz`, start a second `smoke-compose.sh` concurrently. Because the PoC publishes fixed host ports, this second run must fail promptly with a bind/port-allocation collision instead of stopping or reusing the first run.
4. Confirm the first smoke remains healthy after the failed overlapping run and completes successfully.
5. Confirm the sentinel keeps the same container ID and volume name, remains running, and retains its marker contents throughout the smoke.

The sentinel itself is disposable and is removed by the wrapper after the assertions. Its project name is generated for that CI process, so this proof does not target a developer or operator project. The overlapping run also uses the normal per-run project generation in `smoke-compose.sh`; its cleanup therefore has no authority over the first run or the sentinel.

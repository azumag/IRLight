# Structured log redaction audit

Issue #11 requires JSON structured logs to be correlatable without persisting stream keys, SRT passphrases, authentication tokens, passwords, or other credentials. `apps/control-api/log_redaction_inspect_cli.py` is a read-only JSONL audit guardrail for captured logs before they are retained or attached to an incident.

## Usage

Pipe a captured JSONL stream through the inspector. The command reads stdin only, so it does not resolve or print the source pathname.

```sh
python apps/control-api/log_redaction_inspect_cli.py < captured.jsonl
```

The output contains only `status`, the number of records considered, and normalized violation counts. Ordinary blank lines are skipped; an oversized line is counted and rejected before blankness is examined. The output never includes log values or field paths. Exit status is `0` for `SAFE`, `2` for `REVIEW_REQUIRED`, and `3` for structurally invalid JSONL.

The baseline schema requires `timestamp`, `level`, `service`, and `event_type`. Correlation fields such as `request_id`, `session_id`, `node_id`, `version`, and `reason_code` remain event-dependent and can be added without changing this audit contract.

To keep the audit itself bounded when it is pointed at malformed or adversarial captures, one JSONL record is limited to 256 KiB of UTF-8 input and nested arrays/objects are limited to 64 levels for inspection. When the CLI has access to stdin's raw buffer, it applies the 256 KiB limit to raw bytes before UTF-8 decoding, so multibyte text cannot consume a larger pre-check record buffer merely because it contains fewer characters. Oversized lines are drained in bounded byte chunks instead of being materialized in full. Invalid UTF-8 is normalized to `INVALID_JSON`; oversized records return `RECORD_TOO_LARGE`; excessive parser or inspection depth returns `NESTING_TOO_DEEP`. These conditions make the overall result `INVALID`, and the source record is neither echoed nor partially reported. In-process callers that supply only a text stream still receive the same final UTF-8 byte-size validation, but the strongest pre-decode memory bound is available through a raw/buffered stream.

## Secret checks

Sensitive key names such as `authorization`, `token`, `stream_key`, `srt_passphrase`, `password`, `api_key`, `access_key`, `access_key_id`, `secret_key`, `client_secret`, and `cookie` must be `null` or one of the explicit redaction placeholders (`[REDACTED]`, `<redacted>`, `***`). The same rule applies recursively to nested objects and arrays. Key matching normalizes case, punctuation separators, ordinary camelCase boundaries, and acronym-to-word boundaries, so names such as `accessToken`, `streamKey`, `apiKey`, `secretKey`, `clientSecret`, `xAPIKey`, `clientIDToken`, and `HTTPAuthorization` are covered by the same policy. Namespaced variants ending in an unambiguous sensitive suffix are covered as well, including compact/all-caps forms where adjacent acronyms cannot be split unambiguously: `oauth2AccessToken`, `x-api-key`, `proxyAuthorization`, `databasePassword`, `relayRTMPStreamKey`, `AWSAPIKey`, `XAPIKEY`, `AWS_SECRET_ACCESS_KEY`, `awsSecretAccessKey`, `AWS_ACCESS_KEY_ID`, `webhookSecretKey`, `WEBHOOKSECRETKEY`, `dbpassword`, and `sessioncookie` are all sensitive. Metric/configuration names that merely contain those words but continue with a non-sensitive suffix, such as `token_count`, `tokenCount`, `password_policy`, `HTTPStatusCode`, `apikeyRotationCount`, `accessKeyRotationCount`, or `secretKeyRotationCount`, are not treated as credentials by this guardrail.

Sensitive query parameters are checked in absolute URLs and URL-like relative values such as `/callback?token=...` or `?apiKey=...`. The same normalized exact-or-sensitive-suffix matching is used for parameter names, including acronym-style camelCase and compact variants such as `xAPIKey`, `clientIDToken`, `AWSAPIKey`, `AWSSecretAccessKey`, or `webhookSecretKey`, so prefixed forms cannot bypass the field-name policy. URL parameters also have a narrow provider-specific policy for credential-bearing signed URLs: AWS SigV4 `X-Amz-Credential`, `X-Amz-Signature`, and `X-Amz-Security-Token` must be redacted in query strings and fragments. This provider-specific rule is deliberately URL-only; generic field names such as `signature_algorithm` or `credential_format` are not classified as secrets merely because they contain those words. Sensitive parameters in URL fragments, such as OAuth-style `#access_token=...`, are checked by the same redaction rule, including fragment-only values captured without the rest of the URL. Absolute URLs containing userinfo (`scheme://user@host` or `scheme://user:password@host`) always require review; producers should omit the userinfo rather than trying to retain a credential-shaped URL in logs. Duplicate JSON object keys and non-finite JSON numbers are rejected so a producer cannot hide a sensitive field behind parser-dependent behavior.

This is a detection guardrail, not a sanitizer. It does not rewrite logs and must not be used to make an unsafe record safe after the fact. It also cannot reliably infer secrets embedded in arbitrary free text or URL path segments. Producers still need allow-list logging and redaction at the point where a record is constructed; an audit result of `SAFE` is not proof that arbitrary message text contains no secret.

## Incident handling

If the result is `REVIEW_REQUIRED` or `INVALID`, do not upload the captured JSONL to an issue, chat, or ticket. Keep the source in the existing restricted incident location, identify the producer from operational context, fix the producer-side redaction/schema problem, and repeat the audit against a newly captured sample. Secret rotation decisions remain part of the secret-leak runbook; this command intentionally performs no credential, provider, billing, or runtime mutations.
